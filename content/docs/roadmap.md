# Roadmap and status

Everything below describes a **lab-grade devnet**. Dates are in US Eastern time.

## Working and verified

- Deterministic state machine and signed transactions (secp256k1, low-S, nonces, fees).
- Storage: manifests, plans, market and archive deals, multi-replica assignment, accept timeout, per-replica payment.
- Proofs of storage with per-provider challenges, missed-proof counting, slashing of 10% of a replica's collateral and automatic repair.
- Access control with signed read tokens, grants, revocation (effective within about 5 seconds) and client-side `vle1` encryption with per-grantee key envelopes.
- Optional CometBFT mode with an equal-power validator set (a 3-validator network was run on Fly and verified, then retired).
- Public devnet on Fly.io: `e2e-remote` 44/44 and `e2e-private` 24/24 on 2026-10-25 at about 12:40 PM. Replication (11/11) and repair (15/15) passed earlier on the previous chain with extra providers.
- TypeScript client ported to the browser, tested against vectors generated by the Go code.

## What the devnet is right now

One validator on the timer engine, one provider, one volume each. No high availability. The chain was reset on 2026-10-25. The end-to-end scripts left test files and deals on it, so you will see them in the explorer.

## Not built yet

- Validator staking, validator-set changes, validator slashing, state sync, a fee market.
- A Merkle commitment of state (the app hash is an incremental hash, so no light-client proofs).
- Stronger challenge randomness than the public app hash.
- Real ICS-20 transfers; only the payments-only policy and a lab voucher exist.
- Deal renewal, partial-range decryption, forward secrecy, key rotation without re-uploading.
- A retrieval market, provider reputation and price discovery.
- An external security review.

## Possible next steps

- More providers on the public devnet, so replication and repair can be tried by anyone.
- A browser-friendly CORS setting on the provider (`ALLOW_ORIGIN`) so the vault can talk to it directly instead of through the proxy.
- A faucet with a shared rate-limit store, so limits hold across server instances (today they are best effort, see [the faucet guide](/docs/guides/faucet)).
- Key import between the CLI keyring and the web vault.

These are ideas, not promises.
