# Chunking and Merkle roots

An **object** is a file split into chunks of 256 KiB (262,144 bytes) by default. Every object is identified by its **root**, a 32-byte hash that commits to every chunk, the object size and the chunk size. Change one bit anywhere and the root changes.

## The tree

```text
leaf_i = sha256(0x00 || chunk_i)
node   = sha256(0x01 || left || right)
tree   = Merkle tree hash of the leaves: split at the largest power of two below n (RFC 6962 style),
         so any chunk count works without padding
root   = sha256(0x02 || tree || size (8 bytes, big-endian) || chunk_size (8 bytes, big-endian))
```

The `0x00` and `0x01` prefixes separate leaves from interior nodes, so a leaf can never be passed off as a node. The final `0x02` hash binds the size and chunk size, so the root alone pins the exact bytes and layout.

The exact encoding is checked against the Go implementation by test vectors: the TypeScript code in this site's vault is tested against ciphertexts, roots and signatures generated by `tools/tsvectors` in the main repository.

## The manifest

`storage/CommitManifest` publishes the metadata for a root:

```json
{
  "root": "00a361462d4fe0e26aca81144c76a26a1ba6f486f414e3b346f91c26dd46acc4",
  "size": 300000,
  "chunk_size": 262144,
  "mime": "application/octet-stream",
  "name": "e2e-plain-300000.bin",
  "owner": "vault10r2hysg8036ua7au2qu2u9v4vhky2q649a5lht",
  "height": 812
}
```

Encrypted objects add `"encryption": "vle1"` and the owner's `key_envelope`. The name, size and MIME type are **public**, so choose file names accordingly.

For an encrypted object, the chunks and the root are computed over the **ciphertext**. Providers and proofs never see plaintext.

## Inclusion proofs

A Merkle proof for chunk `i` is the list of sibling hashes from the leaf to the tree root. Anyone holding the manifest can recompute the root from the chunk and its proof. This is what makes two things possible:

- **Verified uploads.** The browser sends each chunk with its proof in the `X-Vault-Proof` header, and the provider verifies the whole object against the root before keeping it.
- **Storage challenges.** The chain asks a provider for one chunk and its path, and verifies it against the committed root. See [proofs and slashing](/docs/concepts/proofs-and-slashing).

Downloads are verified too: the vault rebuilds the root from the downloaded chunks and refuses data that does not match the on-chain manifest.
